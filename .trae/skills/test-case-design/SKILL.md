# 测试用例设计 Skill

## 功能描述

为项目生成全面的测试用例，包括单元测试、集成测试和端到端测试，支持TDD开发方法，确保项目质量。

## WHEN

当需要设计测试用例时调用此Skill。

## 输入参数

| 参数 | 类型 | 描述 | 必需 |
|------|------|------|------|
| features | array | 特性ID列表 | 是 |

## Workflow

按照以下步骤执行：

### Step 1: 收集特性清单

- **列出所有特性**：使用 `file-operation.listDirectory()` 读取 `design/features/` 目录
- **记录特性总数**：记录每个特性的ID和名称
- **检查 features 参数**：如果传入的 features 列表为空，使用目录中的所有特性

### Step 2: 完整性检查

- **生成检查清单**：创建表格记录每个特性的处理状态

| 特性ID | 特性名称 | 需求文档 | 测试用例文件 | 状态 |
|--------|----------|----------|--------------|------|
| feature-001 | {名称} | ✅ | ⏳ | 待处理 |
| feature-002 | {名称} | ✅ | ⏳ | 待处理 |

- **保存检查清单**：使用 `file-operation.createFile()` 保存到 `design/project_overview/test-coverage-checklist.md`

### Step 3: 逐个处理特性

对每个特性执行以下操作：

#### 3.1 读取文档
- 使用 `file-operation.readFile()` 读取：
  - `design/features/{feature-id}/requirements.md`
  - `design/features/{feature-id}/api.md`（如果存在）

#### 3.2 设计测试策略
- 确定测试范围
- 选择测试类型（单元测试、集成测试、端到端测试）
- 规划测试数据

#### 3.3 编写测试用例
按照以下格式生成测试用例：

```markdown
# {特性名称} 测试用例

## 1. 测试概述
- 测试范围：{范围描述}
- 测试策略：{策略描述}
- 测试环境：{环境描述}
- 特性ID：{feature-id}

## 2. 测试用例列表

### 2.1 单元测试

#### TC-{feature-id}-U-001：{测试场景描述}
- **优先级**：高|中|低
- **前置条件**：{前置条件描述}
- **测试步骤**：
  1. 步骤1
  2. 步骤2
  3. 步骤3
- **预期结果**：{预期结果描述}
- **实际结果**：（待执行后填写）
- **状态**：未执行|通过|失败
- **对应功能**：FR-{feature-id}-xxx
- **对应验收标准**：AC-{feature-id}-xxx

### 2.2 集成测试

#### TC-{feature-id}-I-001：{测试场景描述}
- **优先级**：高|中|低
- **前置条件**：{前置条件描述}
- **测试步骤**：
  1. 步骤1
  2. 步骤2
- **预期结果**：{预期结果描述}
- **实际结果**：（待执行后填写）
- **状态**：未执行|通过|失败

### 2.3 端到端测试

#### TC-{feature-id}-E-001：{测试场景描述}
- **优先级**：高|中|低
- **前置条件**：{前置条件描述}
- **测试步骤**：
  1. 用户操作1
  2. 用户操作2
  3. 用户操作3
- **预期结果**：{预期结果描述}
- **实际结果**：（待执行后填写）
- **状态**：未执行|通过|失败

## 3. 边界条件测试

#### TC-{feature-id}-B-001：{边界场景描述}
- **测试类型**：边界值|异常处理|压力测试
- **测试步骤**：{步骤描述}
- **预期结果**：{预期结果描述}

## 4. 测试数据
- 测试数据1：{数据描述}
- 测试数据2：{数据描述}

## 5. 测试覆盖率目标
- 单元测试覆盖率：{目标百分比}
- 集成测试覆盖率：{目标百分比}
- 功能测试覆盖率：{目标百分比}
```

#### 3.4 保存测试用例
- **使用 `file-operation.createFile()`** 保存到 `design/features/{feature-id}/test-cases.md`
- **验证文件创建**：确认文件存在且内容完整
- **更新检查清单**：将状态从"待处理"改为"✅ 已生成"

### Step 4: 完整性验证

- **检查所有特性**：确认每个特性都有对应的 `test-cases.md` 文件
- **更新检查清单**：将最终清单保存到 `design/project_overview/test-coverage-checklist.md`
- **记录输出文件列表**：准备返回给调用者

### Step 5: 完成

- **生成完成报告**：

```
[测试用例设计完成]
完成时间：{timestamp}
特性数量：{n}
测试用例总数：{n}
完整性检查：
- feature-001: ✅ 已生成
- feature-002: ✅ 已生成
文档列表：
- design/features/feature-001/test-cases.md
- design/features/feature-002/test-cases.md
下一步：提交测试评审
```

## 输出

**Files created/modified:**
- `design/features/{feature-id}/test-cases.md` - 每个特性的测试用例
- `design/project_overview/test-coverage-checklist.md` - 完整性检查清单

**Status communication:**
- `SUCCESS`: 所有测试用例生成完成
- `WARN`: 部分特性缺少测试用例
- `ERROR`: 发生错误

## 重要规则

### 文件操作要求
- **必须使用 `file-operation` Skill** 创建所有测试用例文件
- **禁止**使用文字描述"假装"创建文件
- 每次创建文件后，必须验证文件是否存在且内容完整

### 完整性要求
- **必须为每个特性都生成测试用例**
- 如果某个特性缺少测试用例，这是高优先级问题
- 完成报告必须包含完整性检查结果

### TDD 衔接要求
测试用例必须：
- 清晰明确，可直接翻译成代码
- 包含足够的细节
- 覆盖所有验收标准
- 考虑边界情况
