# 标准规范（L2）

本文档整合了 Agent 领地划分、编码规范、代码质量标准、强制行为模式、状态管理和 API 完整性等标准规范。

---

## 1. Agent 领地划分

### 1.1 领地划分

| Agent | 领地目录 | 职责说明 |
|-------|---------|---------|
| Architect | design/ | 系统设计、API合同、技术选型 |
| DBA | database/ | 数据模型、数据库管理、SQL优化 |
| Frontend Dev | src/client/ | 前端业务代码、UI组件、用户交互 |
| Backend Dev | src/server/ | 后端业务代码、API实现、数据库操作 |
| DevOps | infra/ | 环境配置、CI/CD流程、依赖管理 |
| QA | tests/ | 测试代码、测试用例、质量评估 |
| Team Lead | 全局协调 | 任务分配、进度追踪、流程控制 |
| Feature Analyst | design/features/ | 特性需求分析、文档编写 |
| req-reviewer | 评审 | 需求文档评审 |
| design-reviewer | 评审 | 设计文档评审 |
| test-reviewer | 评审 | 测试文档评审 |
| code-reviewer | 评审 | 代码评审 |

### 1.2 权限约束

**禁止操作**：
- Frontend/Backend Dev **禁止**修改 package.json、package-lock.json
- Frontend/Backend Dev **禁止**执行 npm install/add 命令
- Frontend/Backend Dev **禁止**修改 database/ 目录
- Frontend/Backend Dev **禁止**修改 infra/ 目录

**专属权限**：
- 只有 DevOps 可以管理依赖和技术栈
- 只有 DBA 可以修改数据库结构
- 只有 Team Lead 可以进行任务分配和进度追踪

**通用约束**：
- 所有 Agent 必须遵循领地划分，禁止跨领地操作
- 跨领地操作必须通过 Team Lead 协调

## 2. 编码规范

### 2.1 命名规范

| 类型 | 规范 | 示例 |
|------|------|------|
| 文件/文件夹 | kebab-case | `user-service.ts`、`login-form.vue` |
| 类/组件 | PascalCase | `UserService`、`LoginForm` |
| 变量/函数 | camelCase | `userName`、`getUserInfo` |
| 常量 | UPPER_SNAKE_CASE | `MAX_RETRY`、`API_BASE_URL` |

### 2.2 长度规范

- 函数长度：不超过 50 行
- 类/组件长度：不超过 300 行
- 文件长度：不超过 500 行
- 嵌套深度：不超过 3 层

### 2.3 注释规范

- **公共 API**：使用 JSDoc 注释，包含参数说明、返回值说明
- **复杂逻辑**：添加解释性注释，说明设计意图和决策理由
- **文件头部**：包含文件用途、作者、创建日期
- **维护规范**：更新代码时同步更新注释

### 2.4 语言规范

- **TypeScript**：启用 strict 模式，避免 any 类型
- **Python**：遵循 PEP8 规范，使用 type hints

## 3. 代码质量标准

### 3.1 准确性标准

- 生成代码必须通过语言编译/解释器检查
- 所有代码可立即运行
- 边界条件处理完整
- 错误处理机制健全

### 3.2 类型安全标准

- TypeScript：启用 strict 模式，避免 any 类型，优先使用接口定义数据结构
- Python：使用 type hints，使用 dataclasses 定义数据结构

### 3.3 错误处理标准

- 捕获具体异常，不使用 bare except
- 异常信息包含上下文，必要时记录日志
- 异常不泄露敏感信息

### 3.4 测试策略

| 测试类型 | 目的 | 覆盖率目标 |
|---------|------|-----------|
| 单元测试 | 测试单个函数和组件 | 核心业务逻辑 ≥80% |
| 集成测试 | 测试模块间的交互 | API调用、数据库操作 |
| 端到端测试 | 测试完整的用户流程 | 关键用户路径 |

**测试质量要求**：
- 测试独立，不相互依赖
- 测试名称描述清晰
- 测试必须可重复执行

### 3.5 代码审查标准

**审查要点**：代码正确性、可读性、性能优化、安全性、代码重复度

**审查流程**：至少1人审查通过才能合并，审查意见必须全部解决

## 4. 强制行为模式

### 4.1 确认机制

**必须确认的操作**：
- 文件删除操作、配置文件修改、批量代码重构
- 版本控制操作（如强制推送）、技术栈变更
- 数据模型变更、敏感信息操作

**确认流程**：
1. 明确告知用户即将执行的操作
2. 说明操作的风险和影响
3. 等待用户明确确认后再执行
4. 记录确认信息到记忆系统

### 4.2 询问机制

**必须询问的情况**：
- 需求不明确时、遇到歧义时、发现潜在问题时
- 需要用户决策时、达到迭代上限时

### 4.3 日志记录

**必须记录的内容**：错误信息、异常情况、关键决策、任务状态变更、迭代次数记录

**日志规范**：包含时间戳、操作人（Agent）、操作内容、结果状态

### 4.4 迭代控制

- 每个评审环节最多迭代 3 次
- 使用记忆系统记录迭代次数
- 达到 3 次迭代仍未通过时，自动升级给用户决策

### 4.5 文件操作规范

**必须使用** `file-operation` **Skill** 进行所有文件操作：

| 场景 | 操作 | Skill调用 |
|------|------|-----------|
| 创建文档 | 创建新文件 | `file-operation.createFile()` |
| 修改文档 | 修改已有文件 | `file-operation.modifyFile()` |
| 删除文件 | 删除文件 | `file-operation.deleteFile()` |
| 创建目录 | 创建新目录 | `file-operation.createDirectory()` |
| 删除目录 | 删除目录 | `file-operation.deleteDirectory()` |
| 读取文件 | 读取文件内容 | `file-operation.readFile()` |

**禁止**：
- 使用文字描述"假装"创建文件
- 在 Agent 或 Skill 内部直接使用 `fs` 模块

**文件操作格式**：
```
[文件操作]
- 操作：创建/修改/删除
- 文件：路径
- 内容：摘要
- 调用：file-operation.createFile({...})
```

**验证要求**：
- 操作完成后必须验证文件确实存在
- 验证文件内容与预期一致

### 4.6 响应规范

**任务开始**：
```
[任务]
- 分析：需求
- 计划：步骤
- 预计：完成预期
```

**任务完成**：
```
[完成]
- 内容：产出
- 使用：说明
- 建议：优化方向
```

## 5. 状态管理

### 5.1 状态类型定义

**流程状态（workflow_status）**：

| 状态值 | 说明 | 转换时机 |
|--------|------|----------|
| `initialized` | 已初始化 | 项目创建时 |
| `in_progress` | 进行中 | 开始第一步时 |
| `paused` | 已暂停 | 用户中断时 |
| `completed` | 已完成 | 所有步骤完成 |
| `cancelled` | 已取消 | 用户取消时 |

**步骤状态（step_status）**：

| 状态值 | 说明 | 转换时机 |
|--------|------|----------|
| `pending` | 未开始 | 步骤创建时 |
| `in_progress` | 进行中 | 步骤开始执行 |
| `waiting_review` | 等待评审 | 提交评审时 |
| `approved` | 已通过 | 评审通过 |
| `rejected` | 未通过 | 评审不通过 |
| `completed` | 已完成 | 步骤完成 |
| `skipped` | 已跳过 | 用户跳过 |

### 5.2 断点续传机制

**保存断点**：当项目被中断时，自动保存当前步骤编号、所有步骤的当前状态、进行中文档的路径、迭代次数记录

**恢复断点**：读取 `project/{project_id}/state`，确定当前步骤，检查前置步骤是否完成，从当前步骤继续

### 5.3 状态优先原则

| 判断依据 | 优先级 | 说明 |
|---------|--------|------|
| mcp_Memory记录 | 高 | 权威来源 |
| 文件存在性 | 低 | 仅作为参考 |
| 用户指示 | 最高 | 覆盖所有规则 |

### 5.4 评审 Agent 调用规则

| 步骤 | Agent | 说明 |
|------|-------|------|
| 步骤4 | @req-reviewer | 需求评审 |
| 步骤12 | @design-reviewer | 设计评审 |
| 步骤17 | @test-reviewer | 测试评审 |
| 步骤21 | @code-reviewer | 代码评审 |

**验证失败处理**：
1. 如果未调用 Agent 而直接完成评审，标记步骤状态为 `invalid`
2. 输出错误信息
3. 要求重新执行并正确调用 Agent

## 6. API 完整性

### 6.1 检查清单

每个 API 设计必须包含以下检查项：

1. ✅ CRUD操作完整性：每个主要实体必须有 Create/Read/Update/Delete 端点
2. ✅ 数据模型覆盖：所有数据模型表必须有对应的 API
3. ✅ 特性需求覆盖：每个特性需求必须有对应的 API 实现
4. ✅ 输入验证：所有 API 必须有输入参数验证规则
5. ✅ 错误处理：所有 API 必须有错误响应格式定义
6. ✅ 认证授权：所有 API 必须有认证/授权说明
7. ✅ 分页机制：列表类 API 必须有分页说明
8. ✅ 速率限制：所有 API 必须有速率限制说明
9. ✅ 文档完整性：每个 API 必须有示例请求和响应
10. ✅ 版本管理：API 版本策略必须明确

### 6.2 验证流程

1. @architect 完成 API 设计
2. @architect 生成 `api_checklist.md`
3. SOLO Coder 验证清单完整性
4. 所有检查项通过后，才能进入设计评审
5. 向用户展示 API 覆盖情况

## 7. Agent 协作规范

### 7.1 交接规范（HANDOFF）

当 Agent A 将任务交接给 Agent B 时，必须提供：

```
HANDOFF TO: [Agent Name/Role]
CONTEXT: [已完成的工作]
CURRENT STATE: [当前状态]
NEXT STEPS: [下一步操作]
RESOURCES: [相关文件和数据]
DEADLINE: [截止时间]
```

### 7.2 文件位置规范

- 设计文档 → `design/`
- 源代码 → `src/`
- 测试代码 → `tests/`
- 部署配置 → `infra/`

## 8. 验证和防护机制

### 8.1 验证检查点

**步骤完成验证**：
- 步骤完成后必须验证输出文件存在
- 验证文件内容与预期一致
- 记录完成状态到记忆系统

**评审前验证**：
- 评审前必须检查输入文档完整
- 验证所有前置步骤都已完成
- 确认评审条件满足

**开发前验证**：
- 开发前必须验证测试用例存在
- 验证 API 文档完整
- 确认依赖关系已解决

### 8.2 防护规则

**确定性检查**：
- 文件创建后立即验证存在性
- 代码提交前验证语法正确性
- 测试执行前验证测试文件完整

**自动化验证**：
- 使用 linter 检查代码风格
- 使用 type checker 验证类型安全
- 使用 unit test generator 验证覆盖率

**AI 驱动的验证**：
- Agent 评审其他 Agent 的代码
- 代码质量自动评估
- 安全漏洞自动扫描

### 8.3 验证流程

**前置检查**：
```
[验证]
- 检查项：[检查项名称]
- 状态：[通过/未通过]
- 依据：[验证依据]
```

**验证失败处理**：
1. 记录验证失败信息
2. 标记失败原因
3. 升级问题给 Team Lead
4. 等待用户决策

### 8.4 验证记录

**必须记录的验证项**：
- 验证时间戳
- 验证结果（通过/失败）
- 验证依据
- 处理措施

**验证记录格式**：
```json
{
  "verification_id": "v-001",
  "check_item": "输出文件存在性",
  "status": "passed",
  "evidence": "文件已创建：design/project_overview/requirements_spec.md",
  "verified_at": "2026-05-17T10:00:00Z"
}
```

### 8.5 防护措施

**文件操作防护**：
- 删除文件前必须确认无依赖
- 修改文件前必须创建备份
- 批量操作前必须二次确认

**代码执行防护**：
- 高风险命令（rm, DROP）必须二次确认
- 数据库操作必须在沙箱环境验证
- 生产环境修改必须通过审批

**权限控制**：
- 遵循领地划分原则
- 跨领地操作必须通过 Team Lead
- 敏感操作必须记录日志
