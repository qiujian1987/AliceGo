# 代码质量标准（L2）

## 1. 准确性标准

### 1.1 语法正确性
- 生成代码必须通过语言编译/解释器检查
- TypeScript/JavaScript 通过 ESLint 检查
- Python 通过 PEP8 和 pylint 检查
- 所有代码可立即运行

### 1.2 逻辑完整性
- 边界条件处理完整
- 错误处理机制健全
- 资源释放/清理逻辑正确

## 2. 类型安全标准

### 2.1 TypeScript/JavaScript
- 启用 strict 模式
- 避免使用 any 类型
- 优先使用接口定义数据结构
- 使用泛型提高复用性

### 2.2 Python
- 使用 type hints
- 使用 dataclasses 定义数据结构
- 使用 Enum 替代魔法数字/字符串

## 3. 错误处理标准

### 3.1 异常处理
- 捕获具体异常，不使用 bare except
- 异常信息包含上下文
- 必要时记录日志
- 异常不泄露敏感信息

### 3.2 返回值设计
- 优先使用 Result/Either 模式
- 明确错误类型和成功状态
- 提供默认值的 safe fallback

## 4. 性能标准

### 4.1 资源管理
- 及时释放资源（文件、连接、内存）
- 使用连接池复用资源
- 避免内存泄漏

### 4.2 算法效率
- 选择合适的数据结构
- 避免不必要的循环嵌套
- 使用缓存减少重复计算

## 5. 测试策略

### 5.1 测试类型

| 测试类型 | 目的 | 覆盖范围 |
|---------|------|---------|
| 单元测试 | 测试单个函数和组件 | 核心业务逻辑 |
| 集成测试 | 测试模块间的交互 | API调用、数据库操作 |
| 端到端测试 | 测试完整的用户流程 | 关键用户路径 |

### 5.2 测试覆盖率目标

- 核心业务逻辑：≥ 80%
- 公共 API：100%
- 数据模型：100%
- 安全相关代码：100%

### 5.3 测试质量要求

- 测试独立，不相互依赖
- 测试名称描述清晰
- 使用真实数据，避免 mock 过度
- 测试必须可重复执行

## 6. CI/CD 流程

### 6.1 代码提交阶段
1. 代码提交 → 质量检查 → 测试执行

### 6.2 构建部署阶段
2. 构建验证 → 部署准备 → 环境检查

### 6.3 上线阶段
3. 部署执行 → 健康检查 → 回滚机制

## 7. 质量检查工具

### 7.1 前端工具
- **ESLint**：代码风格和语法检查
- **Prettier**：代码格式化
- **TypeScript**：类型检查
- **Stylelint**：CSS 风格检查

### 7.2 后端工具
- **ESLint**：代码风格和语法检查
- **Prettier**：代码格式化
- **TypeScript**：类型检查
- **Jest**：单元测试

## 8. 代码审查标准

### 8.1 审查要点
- 代码正确性
- 代码可读性
- 性能优化
- 安全性
- 代码重复度

### 8.2 审查流程
- 至少1人审查通过才能合并
- 重大变更需要2人审查
- 审查意见必须全部解决
